# Phase 5: Employee lifecycle

- **Status:** planned
- **Depends on:**
  - Phase 0: jobs, audit, `work_queue`, perms
  - Phase 1: Employee, Item and Rule in Postgres; versioned policy; the in-flight publish semantics
  - Phase 2: Document in Postgres, risk tiers, the review queue
  - Phase 4: every external call job- or activity-backed, the outbox, `access.perform`, the Temporal worker and the `temporal.start`/`temporal.signal` relay
- **Design:** [2026-11-01-hardening-design.md](2026-11-01-hardening-design.md) · **ADR:** [0011 Temporal orchestration](../adr/0011-temporal-orchestration.md)

## Goal
Take the same rules engine, document checks, approvals and job backbone that run onboarding, and use them for everything that happens to a worker after the offer, so the product covers the whole workforce lifecycle rather than just onboarding. Built in this order:
1. Role and department transfer
2. Offboarding
3. Compliance rechecks
4. Contractor vs employee, and rehire
5. Leave and return-to-work

The operating principle still holds:
- **Automatic:** starting a case, generating its items, collecting documents, granting or revoking access, reminders, expiry watching.
- **Human, at gates only:** effective dates inside the protected window, high-risk documents, access revocations that fail, exits flagged as sensitive, and overrides. Each of these lands in `work_queue`.

## Key idea: one `lifecycle_case` model
Onboarding today is implicit: an `Employee` has `Item`s generated by `checklist.regenerate(eid)` from rules whose `offset_days` are relative to `joining_date`. Phase 5 makes it explicit and general:
- A **case** has a `type` (`onboarding | transfer | offboarding | recheck | leave | return`), an `effective_date` (the anchor for `offset_days`), a `state`, the employee *snapshot before and after* (the attributes that drive rule matching), and its own items.
- **Rules** gain a `case_type` match key (default `onboarding`, so every existing rule keeps behaving the same). `checklist.build_items(emp, rules, …)` stays pure and unchanged in signature. The case passes `emp = {**employee, **case.after, "joining_date": case.effective_date}`, and `rules` filtered to `case_type`. `match_rule` gains `worker_type` and `case_type` alongside department, role, location, country and grade. **No second rules engine.**
- **Items** gain `case_id`. Existing items are backfilled to an `onboarding` case per employee.
- **One open case per type per employee.** Several types may be open at once: a transfer during a recheck is fine. Offboarding cancels every other open case's undone items under the Phase 1 rule: cancel only what isn't done, never delete evidence.

### State machine (shared by every case type)
```
draft ──open──▶ active ──all required items done──▶ completed
  │               │  ▲
  │            pause│  │resume            (leave only)
  │               ▼  │
  │             paused
  │
  └──cancel──▶ cancelled   (from draft/active/paused; reason required; undone items → Cancelled, evidence kept)
```
- **`draft`:** created but not yet live. Used when the effective date is inside the protected window (`LIFECYCLE_PROTECTED_DAYS`, default 3) or the case is flagged sensitive. A `work_queue` row of kind `lifecycle_gate` is opened for hr_ops. Everything else goes straight to `active`.
- **`active`:** items generated, jobs scheduled.
- **`paused`:** obligations frozen. Due dates aren't counted as overdue, and reminders and escalations skip the item.
- **`completed`:** set automatically by `checklist.recompute` when every non-optional item is done. Completing triggers that case's *completion effects* (below).
- Every transition goes through `lifecycle.service.transition(case_id, to, actor, reason)`, which validates against `ALLOWED = {(from, to): roles}`, writes `case_events` and calls `audit.record`. Nothing writes `state` directly.

### How a case runs: one Temporal workflow per case
Each case is driven by a durable **Temporal workflow** (ADR 0011). The workflow orchestrates; it doesn't hold the case.
- **State stays in Postgres.** `lifecycle_cases.state`, the items and `case_events` are the record. The workflow changes them only through activities that call `lifecycle/service.py` (`transition`, `generate_items`, `complete_if_done`, the completion effects). If a workflow's history is lost, the case is still complete in Postgres, and `workflows.reconcile` restarts the workflow from it.
- **Started through the outbox.** `open_case` writes the case row, its items and `jobs.enqueue("temporal.start", {"workflow": "<Type>CaseWorkflow", "args": [case_id]}, idempotency_key=f"case:{case_id}", conn=c)` **in the same `tx()`**. A case can never exist without its workflow eventually starting, and a retry can't start a second one.
- **Human gates are signals.** Approving a `lifecycle_gate` exception, pausing, resuming, cancelling and "returned early" all write Postgres first, then send `temporal.signal` through the outbox in the same `tx()`. The workflow reacts by re-reading the case through an activity, so a signal tells it to check again; it never carries authoritative data.
- **Workflow ids:** `case:<case_id>` (deterministic). One workflow per case.
- **Side effects:** access grants and revokes, emails and document requests run as activities that use the Phase 4 idempotency keys (`access:<app>:<action>:<email>:<resource>`, `email:<purpose>:<case_id>:…`).

| Case type | Workflow | Orchestration |
|---|---|---|
| `transfer` | `TransferCaseWorkflow` | If the case is in `draft` (protected window), wait for the `gate_approved` signal. Then sleep until `effective_date` (`workflow.sleep` to 00:00 `ORG_TIMEZONE`), activity `replan` (items for `after`, re-planning in-flight onboarding with the Phase 1 semantics), then grant activities for new access and revoke activities for the `access_diff` result. Wait for `items_changed` signals until `complete_if_done`, then apply the completion effect (`employees` → `after`, `employee_history`). |
| `offboarding` | `OffboardingCaseWorkflow` | Gate wait if sensitive or in the protected window. Item activities (assets, handover, settlement) run immediately. `immediate` revokes (termination) run at once. Otherwise a **timer to the last working day, 18:00 local**, then every revoke as an activity, then a timer to `effective_date + 1 day` before revoking the portal token. A revoke that exhausts its retries opens `access_revoke_failed` (4 h SLA). The workflow keeps waiting for that item to be resolved and doesn't fail. |
| `recheck` | `RecheckWorkflow` | Started when a document with an expiry is accepted (key `recheck:<doc_id>`). Sleeps until `expiry - recheck_lead_days`, then opens the recheck case's items and sends the request email, then waits for the renewal to be accepted (an `items_changed` signal from document review). A reminder timer runs weekly until expiry, and at expiry it opens a `compliance_expired` exception. Rules with `recheck_every_days` (e.g. the annual infosec acknowledgement) restart with `continue_as_new` after each cycle. |
| `leave` | `LeaveCaseWorkflow` | Activity `pause_items`. Then **wait for the `returned` signal**, with a timer at the expected return date as a fallback that opens a `return_overdue` exception for HR (it does not resume by itself). On the signal: activity `resume_items` (shifts due dates) and starts the `return` case through the outbox. |
| `return` | `ReturnCaseWorkflow` | Replan for return items (restore access, re-acknowledge changed policies), then complete. |
| `onboarding` | none in this phase | Backfilled onboarding cases keep running on the Phase 1–4 paths. Moving onboarding itself onto a workflow is a later step. |

Contractor/employee and rehire aren't separate workflows. A `worker_type` change opens a transfer case, and a rehire is an onboarding case with reused documents.

## Scope by case type

### 1. Transfer (role, department, location, grade or manager change)
- **Started by:** HR Ops through "Change role" on the employee record, which replaces today's `PATCH /api/employees/{eid}` behaviour of re-planning onboarding in place via `checklist.regenerate(eid, reason)`. It can also come from an HR Portal connector sync that detects a change in role, department, location or manager (`integrations` mapping, idempotent upsert).
- **`before` and `after`:** the five matching attributes plus `manager_email`.
- **Items:**
  - **Added:** rules matching `after` with `case_type='transfer'`, e.g. a new country's tax form, new department policy acknowledgements, access for the new team.
  - **Revoked:** access granted by rules that matched `before` but don't match `after`. This is a *diff of access grants*, not a diff of rules: the grants come from the `access_results` already recorded per employee by `integrations.engine.perform_access`. Each becomes an `access_revoke` task item that's done automatically through `access.perform`.
  - **Already satisfied:** documents still valid under the new rules (same `doc_type`, not expired, accepted) are linked rather than collected again.
- **If onboarding is still in progress:** the onboarding case's undone items are re-planned against `after` using the Phase 1 publish semantics (add new, cancel undone, keep evidence). That replaces the current `regenerate` call; no new logic.
- **Completion effect:** `employees` row updated to `after`, and `employee_history` gets a row (see schema).

### 2. Offboarding
- **Started by:** HR Ops "Start offboarding" with a last working day, an exit type (`resignation | termination | end_of_contract | retirement`) and a `sensitive` flag (an involuntary exit stays confidential until the effective date). It can also come from an HR Portal sync that sets a termination date.
- **Items** come from rules with `case_type='offboarding'`, so they're governed and versioned like any rule. Seeded rules:
  - Access revocation for every grant recorded for the employee. One item per app, run by `access.perform` with a revoke action. Timed to the effective date: `offset_days: 0` and `run_at` = last day 18:00 org time. For `termination` exits, `offset_days` is 0 with `immediate: true`, which means revoke on case open.
  - Return assets: laptop and badge (Facilities and IT owners; manual tasks).
  - Knowledge handover (manager owner).
  - Exit interview (HR; optional).
  - Final settlement / full-and-final (Payroll, `country: IN`); final paycheck notice (`country: US`).
  - Experience/relieving letter issued (HR; task with a generated document template from `EmailTemplate`).
  - Exit documents collected (e.g. resignation acceptance), as document items through the normal intake.
- **Connectors:** `connectors/apps.py` `ACTIONS` gains the revoke counterparts:
  - Slack: `deactivate_account`, `remove_from_channel`
  - Jira: `deactivate_account`, `remove_from_project`
  - Google Workspace: `suspend_account`, `remove_from_group`
  - ServiceNow: `create_ticket` with resource `offboarding`

  Each `_outcome` records the action exactly as grants do today. `perform` stays repeat-safe through `_existing`. A revoke of something never granted is recorded as `status: 'skipped'` with message "nothing to revoke", not as a failure.
- **Gates:**
  - A revoke that goes dead in the queue opens a `work_queue` exception `access_revoke_failed` for admin, with high priority and an SLA of 4 h. An ex-employee keeping access is the top security risk in this phase.
  - A `sensitive` case is visible only to admin and hr_ops until its effective date. Managers and auditors see it from then on; the manager sees it on the day.
- **Completion effect:** employee `status='exited'`, `exited_at`; they're excluded from the dashboard by default (there's a filter to show them). The portal token is revoked: `/api/portal/{token}` returns 410 "This onboarding link is no longer active". Documents are kept under a retention policy, which is out of scope here (see non-goals).

### 3. Compliance rechecks
- **Started by:** a `RecheckWorkflow`, started through the outbox (key `recheck:<doc_id>`) when a document whose `doc_type.expires` is true is accepted. It sleeps until `extracted.expiry_date - RECHECK_LEAD_DAYS` (per doc type, default 60; visa and work permit 90). Rules with a periodic `recheck_every_days` (e.g. annual infosec acknowledgement, certification renewal) use the same workflow with `continue_as_new`. As a safety net, the daily `lifecycle.reconcile` job starts any missing recheck workflow.
- **Behaviour:** opens a `recheck` case with one item per expiring document, keyed `recheck:<employee>:<doc_type>:<expiry_date>`, so one expiry produces one case no matter how many times the workflow or the reconcile job runs. The request email goes out through the outbox, keyed `email:recheck:<case id>`. The upload runs through the normal intake, so Phase 2 risk tiers apply: a visa is high-risk, so a human always decides.
- **Escalation:** if the new document isn't accepted 14 days before expiry, a `work_queue` row `compliance_expiry` goes to hr_ops. On the expiry date itself, a critical row goes to admin and hr_ops. The item becomes `overdue`, and the dashboard shows the employee as "Compliance at risk".
- **Validation reuse:** `validate.evaluate` already flags `expires` documents with `exp < joining`. For rechecks, the anchor date is the case's `effective_date` (the old expiry), not joining, using the same code path with the snapshot `joining_date` set to the anchor.

### 4. Contractor vs employee, and rehire
- **`worker_type`** (`employee | contractor | intern`) becomes an employee attribute and a rule match key. `match_rule` adds it to its loop over keys, so one line changes. Seeded rules add contractor-specific items (MSA/SOW on file, contractor NDA, an end-of-contract offboarding case scheduled automatically from `contract_end_date`) and exclude employee-only items (PF/benefits enrolment) using `worker_type: employee`.
- **Conversion** from contractor to employee is a transfer case where `worker_type` changes, so it gets the transfer diff (add employee-only items, revoke contractor-only access) for free.
- **Rehire:**
  - **Detection:** when a joiner is created (import, connector, or the `integrations.engine._ensure_joiner` path), it matches an existing `exited` employee by normalised email or by (name + date of birth). An exact email match links automatically; a name + DOB match opens a `work_queue` row `rehire_match` for hr_ops to confirm or reject, because a false merge mixes two people's records.
  - **Once confirmed:** the new onboarding case is created on the *same* employee id (history preserved), `rehire_count += 1`.
  - **Document reuse:** previously accepted documents are reused when they're of the same `doc_type`, not expired by the new joining date, and the doc type's `reusable_on_rehire` is true. Defaults: true for PAN, education and photo ID with expiry checked; false for address proof, bank letter and BGV. Reused items are created as `Accepted` with reason "Reused from previous employment (document <id>, accepted <date>)", with a link to the original Document. Nothing is copied.
  - BGV rules can require a fresh check when the gap since exit is more than N days (rule `match: {rehire_gap_days_min: 180}`).

### 5. Leave and return-to-work
- **Started by:** HR Ops "Record leave" with a type (`parental | medical | sabbatical | unpaid | other`), start date and expected return date. It can also come from an HRIS sync.
- **Leave case:**
  - Opening it pauses every *other* active case's items that aren't marked `continues_on_leave` (an expiring visa recheck continues, for example; training acknowledgements pause).
  - Paused items keep their due date but are excluded from overdue and escalation.
  - Optionally suspends access: rule `case_type='leave'`, e.g. suspend the VPN for leave longer than 30 days.
- **Return:**
  - The `LeaveCaseWorkflow` waits for the `returned` signal, which is sent when HR records the actual return. It does **not** resume by itself on the expected return date. Instead a timer at that date opens a `return_overdue` exception for HR. On the signal, it opens the `return` case.
  - Return items come from rules with `case_type='return'`: restore suspended access, re-acknowledge policies whose version changed while the person was away (compares the `PolicyAck` version to the current one), and a return-to-work meeting with the manager.
  - Paused items resume, and **their due dates shift by the length of the leave**. That's computed when they resume and recorded as a `case_event` per item.
- **Extended leave:** past the expected return date + 7 days with no return recorded, a `work_queue` row `leave_overdue` goes to hr_ops.

## Non-goals
- Payroll calculation, leave balances or accruals. We track that a leave *exists* and its effect on obligations, not entitlement.
- Document retention and deletion schedules (legal-hold aware). These need a legal retention matrix per country; tracked as a follow-up ADR.
- Real vendor API calls for app connectors. They stay demo connectors that record what they *would* do, as today. Swapping in the Slack, Jira or Google SDK per app is a separate task per vendor; the action names are designed to match the real APIs.
- Org-chart management. Manager is a field on the employee, and Phase 6 builds manager scoping on it.
- Self-service resignation by employees. HR starts offboarding.

## Schema

```sql
-- 030_lifecycle.sql
CREATE TYPE case_type  AS ENUM ('onboarding','transfer','offboarding','recheck','leave','return');
CREATE TYPE case_state AS ENUM ('draft','active','paused','completed','cancelled');

CREATE TABLE lifecycle_cases (
  id              text PRIMARY KEY,                       -- 'case_' + short id
  employee_id     text NOT NULL REFERENCES employees(id),
  type            case_type NOT NULL,
  state           case_state NOT NULL DEFAULT 'draft',
  effective_date  date NOT NULL,                          -- anchor for rule offset_days
  end_date        date,                                   -- leave expected return / contract end
  subtype         text,                                   -- exit type, leave type, recheck doc_type
  before          jsonb NOT NULL DEFAULT '{}',            -- matching attributes before
  after           jsonb NOT NULL DEFAULT '{}',            -- matching attributes after
  sensitive       boolean NOT NULL DEFAULT false,
  rule_version_id bigint REFERENCES rule_versions(id),   -- the published policy version items were built from
  idempotency_key text UNIQUE,                            -- e.g. recheck:E1001:visa:2027-02-01
  opened_by       text NOT NULL,                          -- user id or 'system'
  opened_at       timestamptz NOT NULL DEFAULT now(),
  closed_at       timestamptz,
  close_reason    text
);
CREATE UNIQUE INDEX one_open_case_per_type
  ON lifecycle_cases (employee_id, type) WHERE state IN ('draft','active','paused');
CREATE INDEX cases_by_state ON lifecycle_cases (state, type);

CREATE TABLE case_events (                                 -- transitions + per-item lifecycle effects; append-only
  id          bigserial PRIMARY KEY,
  case_id     text NOT NULL REFERENCES lifecycle_cases(id),
  at          timestamptz NOT NULL DEFAULT now(),
  actor       text NOT NULL,
  kind        text NOT NULL,                              -- transition | item_added | item_cancelled | item_paused | item_resumed | due_shifted | doc_reused | access_revoked
  from_state  case_state,
  to_state    case_state,
  item_id     text,
  detail      jsonb NOT NULL DEFAULT '{}'
);
CREATE INDEX case_events_case ON case_events (case_id, at);

-- 031_items_lifecycle.sql
ALTER TABLE items ADD COLUMN case_id text REFERENCES lifecycle_cases(id);
ALTER TABLE items ADD COLUMN paused_at timestamptz;
ALTER TABLE items ADD COLUMN continues_on_leave boolean NOT NULL DEFAULT false;
ALTER TABLE items ADD COLUMN reused_document_id text REFERENCES documents(id);
ALTER TABLE items ADD COLUMN action jsonb;                -- for access_revoke/grant task items: {app_id, action, resource}
CREATE INDEX items_case ON items (case_id);

-- 032_employees_lifecycle.sql
ALTER TABLE employees ADD COLUMN worker_type text NOT NULL DEFAULT 'employee'
  CHECK (worker_type IN ('employee','contractor','intern'));
ALTER TABLE employees ADD COLUMN status text NOT NULL DEFAULT 'onboarding'
  CHECK (status IN ('onboarding','active','on_leave','offboarding','exited'));
ALTER TABLE employees ADD COLUMN contract_end_date date;
ALTER TABLE employees ADD COLUMN exited_at date;
ALTER TABLE employees ADD COLUMN rehire_count int NOT NULL DEFAULT 0;
ALTER TABLE employees ADD COLUMN portal_token_revoked_at timestamptz;

CREATE TABLE employee_history (                          -- one row per effective change; answers "what was X's role on date D"
  id           bigserial PRIMARY KEY,
  employee_id  text NOT NULL REFERENCES employees(id),
  valid_from   date NOT NULL,
  valid_to     date,                                      -- null = current
  attrs        jsonb NOT NULL,                            -- department, role, grade, location, manager_email, worker_type
  case_id      text REFERENCES lifecycle_cases(id),
  recorded_by  text NOT NULL,
  recorded_at  timestamptz NOT NULL DEFAULT now(),
  EXCLUDE USING gist (employee_id WITH =, daterange(valid_from, valid_to) WITH &&)   -- needs btree_gist
);

-- 033_rules_lifecycle.sql  (rule_versions.body is jsonb from Phase 1; these are documented keys, validated in policy/service.py)
--   match.case_type         'onboarding' (default) | 'transfer' | 'offboarding' | 'recheck' | 'leave' | 'return'
--   match.worker_type       'employee' | 'contractor' | 'intern' | list
--   match.exit_type         list, offboarding only
--   match.leave_min_days    int, leave only
--   match.rehire_gap_days_min int
--   immediate               bool, offboarding: run on case open instead of offset from effective date
--   continues_on_leave      bool
--   recheck_every_days      int
--   access                  {app_id, action, resource} for grant/revoke task items
-- doc_types gain: recheck_lead_days int, reusable_on_rehire bool
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

## API endpoints
| Method & path | Purpose | Roles |
|---|---|---|
| `GET /api/employees/{eid}/cases` | all cases with state and progress | admin, hr_ops, approver, auditor; manager for own reports (Phase 6); `sensitive` cases hidden from manager and auditor until effective |
| `GET /api/cases?type=&state=&due_before=` | cross-employee case list | admin, hr_ops, approver, auditor |
| `GET /api/cases/{id}` | case, items, events, the access diff | as above |
| `POST /api/cases/preview` | `{employee_id, type, effective_date, after, subtype}` → items that would be added, cancelled, revoked or reused, with **no writes**. Uses the same preview function as Phase 1 rule publishing. | admin, hr_ops |
| `POST /api/employees/{eid}/transfer` | `{effective_date, after, reason}` → case (draft if inside the protected window) | admin, hr_ops |
| `POST /api/employees/{eid}/offboard` | `{last_day, exit_type, sensitive, reason}` | admin, hr_ops |
| `POST /api/employees/{eid}/leave` | `{type, start_date, expected_return, reason}` | admin, hr_ops |
| `POST /api/employees/{eid}/return` | `{actual_return}`, closes the leave case and opens the return case | admin, hr_ops |
| `POST /api/cases/{id}/transition` | `{to, reason}` (open from draft, cancel, pause, resume), checked against `ALLOWED` | admin, hr_ops; `open` of a sensitive or protected-window draft also allowed for approver |
| `POST /api/rehire-matches/{work_queue_id}/resolve` | `{decision: 'link'|'new_person', reason}` | admin, hr_ops |
| `GET /api/compliance/expiring?days=90` | upcoming expiries across employees | admin, hr_ops, approver, auditor |
| `GET /api/portal/{token}` | **changed:** 410 if `portal_token_revoked_at` is set; shows only the joiner-facing items of active cases | public (token) |

`PATCH /api/employees/{eid}` keeps working for *corrections* (typos, a wrong DOB), which aren't lifecycle events. Changing any of the matching attributes through PATCH now returns 409 "Use Change role to move someone; it plans access and documents for the new role", and the UI routes to the transfer dialog. This prevents silent re-planning, a gap flagged in the review.

## Screens

### Employee record (`frontend/app/(hr)/employees/[id]/page.tsx`)
- **Header:**
  - A `status` badge (Onboarding, Active, On leave, Offboarding, Exited) and a `worker_type` badge.
  - A **Lifecycle** actions menu (`dropdown-menu`): Change role…, Record leave…, Record return…, Start offboarding…
  - Items are hidden by status and role; e.g. no Record leave while exited, and hidden for auditor and manager.
- **New "Cases" tab**, the first tab once more than one case exists:
  - A vertical timeline of cases, newest first. Each card shows type icon, state pill, effective date, progress bar (same component as the dashboard readiness bar), and an "N need attention" count.
  - Expanding a card shows its items grouped by Documents, Tasks and Access.
  - **Access rows** show the app, the action (grant or revoke), and a status of pending, done, skipped or failed. A failed row links to its work_queue exception.
- **Dialogs.** Every lifecycle dialog has **two steps: details → preview → confirm.** The preview comes from `POST /api/cases/preview` and shows:
  - green "Will add" items
  - red "Will revoke" access
  - grey "Will cancel" (undone items only)
  - blue "Reused" documents
  - an amber banner "Effective in 2 days; goes to an HR approver before it takes effect" when inside the protected window

  Confirm is disabled until the preview has loaded.
- **Leave:** paused items render dimmed with a "Paused (on leave)" chip and their original due date crossed out once it shifts.
- **Exited employees:** a read-only banner, "Exited on 2026-12-31 · offboarding completed". Actions are hidden and evidence stays viewable.

### Dashboard (`frontend/app/(hr)/dashboard/page.tsx`)
- The status filter gains Active, On leave, Offboarding and Exited. Exited is hidden by default.
- A new tile **"Compliance at risk"**: the count of employees with a recheck item under 14 days from expiry, linking to the compliance list.
- A new tile **"Leaving this month"**: offboarding cases with an effective date this month. Admin and hr_ops only, so it never reveals sensitive exits to others.

### Compliance (`frontend/app/(hr)/compliance/page.tsx`, new): admin, hr_ops, approver, auditor
- A table of upcoming expiries: employee, document type, expiry date, days left (coloured: < 14 red, < 60 amber), recheck case state, and the new document's status.
- Filters: doc type, department, location, window of 30, 60 or 90 days.
- Empty state: "No documents expire in the next 90 days."

### Portal (`frontend/app/portal/[token]/page.tsx`)
- Shows active cases relevant to the joiner: onboarding, recheck ("Your work permit expires on 1 Feb 2027; please upload the renewed permit"), and return (policy re-acknowledgements).
- Offboarding is never shown in the portal; that's HR-driven.
- A revoked token shows a friendly 410 page.

| `backend/lifecycle/service.py` (new) | `open_case(eid, type, effective_date, after, subtype, actor, reason, key=None)`: computes the snapshot, picks draft or active (protected window, sensitive), builds the items, writes the `case_events`, and enqueues the `temporal.start` for `case:<id>` **in the same transaction**. ## Migration steps
1. Apply 030–033. They're additive, and existing behaviour is unchanged because no rule has `case_type` set yet and the default is onboarding.
2. **Backfill onboarding cases.** For every employee, create `lifecycle_cases(type='onboarding', effective_date=joining_date, state=completed|active)`, with state from whether every item is done. Then set `items.case_id`. Idempotency key `backfill:onboarding:<eid>`. Parity check: the count of items with `case_id IS NULL` is 0.
3. Backfill `employee_history` with one open row per employee from current attributes. Backfill `worker_type`: interns from grade G1 and role containing "Intern", employee otherwise; flag any ambiguous ones in the migration report.
4. Publish the new lifecycle rules as a **policy version through the Phase 1 draft → preview → approve flow**, not a raw seed insert in production. The preview must show 0 changes to in-flight onboarding (they're all `case_type` ≠ onboarding). That's the proof the change is safe.
5. Ship the endpoints and screens behind `LIFECYCLE=on`. Register the lifecycle workflows on the worker, then run `lifecycle.reconcile` once in **dry-run** for 2 days (it logs the workflows it *would* start, e.g. rechecks for every already-accepted visa) before switching it on.
6. Switch `PATCH` to 409 for matching attributes in the same release as the transfer dialog.

To roll back, set `LIFECYCLE=off`: the routes are hidden, the reconcile job is unregistered, and running case workflows are cancelled with `cancel` (their Postgres state stays as it was), while the backfilled cases stay as passive metadata. The onboarding UI still works off `items`.

## Risks and rollback
| Risk | Mitigation |
|---|---|
| Revoking access on the wrong day (timezone) cuts someone off early | `effective_date` plus an explicit `ORG_TIMEZONE`. Revokes run at 18:00 local on the last day, except termination (`immediate`). Covered by tests with a fixed clock. |
| A false rehire match merges two people | Only an exact email match auto-links; name + DOB always needs a human. Unlinking is a supported action that splits the cases back by `case_id`. |
| Leave pause hides real compliance obligations | `continues_on_leave` is set on every recheck rule by default; the compliance page ignores pause. |
| Transfer diff revokes access that was granted by hand, not by a rule | The diff only revokes grants recorded with a `rule_id` or `case_id`. Manual grants are listed as "Review manually" in the preview, never auto-revoked. |
| The `PATCH` 409 breaks the existing edit-employee UI | Shipped in the same release as the transfer dialog; the error message points to the right action. |
| A workflow and Postgres disagree | The workflow never holds case data: it re-reads through activities, and every transition is validated by `lifecycle.service.transition`. `lifecycle.reconcile` repairs missing workflows. |
| Long timers (90-day rechecks) outlive a code change | Workflow versioning with `workflow.patched()` for logic changes. Timers survive deploys because Temporal persists them. |
| Rollback | `LIFECYCLE=off` as above. The migrations are additive and the backfill is idempotent; nothing in onboarding depends on cases existing. |
